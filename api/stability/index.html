    Public API and stability¶

    This page is the contract for 1.0. It states which names you can build on, which are experimental, which are internal, and how a public name is retired. The __all__ lists in the source match it; a unit test (tests/unit/test_public_api.py) fails if they drift apart.

    What "public" means¶

    A name is public when it appears in the __all__ of its package or of a module this page lists. Anything else is not covered, even when it is importable and even when the API reference renders it:

    • a name that starts with an underscore;
    • a module that starts with an underscore;
    • a module or name that is not listed here, such as figaroh.calibration.config or figaroh.identification.selection.

    Public names follow semantic versioning: a breaking change to a supported name needs a new major version. Experimental names may change in any minor release.

    Top-level packages¶

    import figaroh imports every package below eagerly, so figaroh.tools.robot and friends work after a bare import. The status column is the status of the package as a whole; the sections below give the detail.

    Notes on judgement calls:

    • figaroh.calibration.calibration_tools is public because the examples build their calibration pipelines on it. The legacy flat-format get_param_from_yaml it used to re-export was removed in 1.0 (see below); figaroh.utils.config_parser.get_param_from_yaml is the parser.
    • figaroh.identification.physical_fit is the module behind select_stage: physical_fit. Its functions are public; its private helpers are not.
    • The figaroh.tools modules randomdata, robotcollisions and robotipopt are public helpers kept for the optimal-design classes.

    Experimental areas¶

    These are importable and tested, but they may change or move in a minor release, and a call can raise NotImplementedError.

    • MuJoCo backend and from_mjcf. MuJoCoBackend needs the optional mujoco package. RobotIdentificationSystem.from_mjcf raises NotImplementedError: MJCF loading is not supported yet. Genesis and Isaac Sim backends are not shipped; get_backend only names them.
    • figaroh.integration. The one-line RobotIdentificationSystem workflow.
    • figaroh.visualisation and figaroh.tools.robotvisualization. Meshcat and plotting helpers.
    • figaroh.measurements. A measurement container that no shipped workflow uses.
    • Log-Cholesky fits (LC1). The log-Cholesky physical fit is not part of the library: the feasibility spike was a no-go for 0.7.0 (D5, issue 155). If it ships, it ships as an opt-in, experimental method.

    Names in these modules, as they stand today:

    • figaroh.integration: RobotIdentificationSystem, IdentificationResult
    • figaroh.visualisation: colors, MeshcatVisualizer
    • figaroh.visualisation.colors: rgb2int, material, red, blue, green, yellow, magenta, cyan, white, black, grey, colormap
    • figaroh.backends.mujoco: MuJoCoBackend
    • figaroh.tools.robotvisualization: VisualizationConfig, RobotVisualizer, place, display_COM, display_axes, rotation_matrix_from_vectors, display_force, display_bounding_boxes, display_joints
    • figaroh.measurements: Measurement

    Internal modules¶

    These support the public API. Do not import them from outside figaroh; they may change or disappear in any release.

    • Any module or name that starts with an underscore, for example figaroh.identification._physical_comparator and figaroh.tools._report_common.
    • figaroh.tools.load_robot (use figaroh.tools.robot, which re-exports load_robot), figaroh.tools.provenance.
    • figaroh.calibration.config, figaroh.calibration.estimation and figaroh.identification.config, figaroh.identification.selection, figaroh.identification.physical_consistency, figaroh.identification.cad_constraints, figaroh.identification.reconstruction and the other modules not listed above. Their main names are re-exported by the packages that list them.
    • figaroh.optimal.config, figaroh.optimal.base_parameter, figaroh.optimal.contraints.
    • figaroh.utils.cubic_spline, figaroh.utils.config_migration (run it as python -m figaroh.utils.config_migration; its functions are internal).
    • figaroh.data.protocol, figaroh.data.source, figaroh.data.observations and figaroh.data.trajectory: import their names from figaroh.data.

    Deprecated¶

    These names still work but emit a DeprecationWarning. Each is deprecated in 1.0 and scheduled for removal in 2.0.

    • figaroh.tools.qrdecomposition.QR_pivoting and double_QR: use QRDecomposer.decompose_with_pivoting and QRDecomposer.double_decomposition;
    • figaroh.tools.robotcollisions.CollisionWrapper (warns on construction): use CollisionManager;
    • the module-level wrappers in figaroh.tools.robotvisualization (place, display_COM, display_axes, rotation_matrix_from_vectors, display_force, display_bounding_boxes, display_joints): use the RobotVisualizer methods;
    • the convenience wrappers plot_calibration_results, plot_identification_results and save_results in figaroh.utils.results_manager: use the ResultsManager methods of the same names;
    • the flat physical_consistency_enabled identification config key: use physical_consistency.enabled.

    Removed in 1.0¶

    These warned for at least one minor release and were removed in 1.0 (issue 185). Each has a migration note in the CHANGELOG.

    • the legacy flat configuration format (deprecated since 0.4.6): loading it raises an error naming python -m figaroh.utils.config_migration, which still reads legacy files to convert them. This removes figaroh.calibration.config.get_param_from_yaml, figaroh.identification.config.get_param_from_yaml, their get_param_from_yaml_legacy wrappers and the get_param_from_yaml re-exports of calibration_tools and identification_tools;
    • get_param_from_yaml_with_warning in the calibration and identification config modules (since 0.2.0);
    • figaroh.utils.config_parser.get_calibration_param_from_yaml and get_identification_param_from_yaml (since 0.2.0): use get_param_from_yaml with task_type;
    • a non-zero regularization_coefficient / coeff_regularize (since 0.6.0): now a ConfigurationError; zero or absent is still accepted.

    Deprecation policy¶

    • A public name is deprecated by emitting a DeprecationWarning that names the replacement. It keeps working for at least one minor release before removal.
    • After 1.0, a public name is removed only in a major release.
    • Every deprecation and removal has a migration note in the CHANGELOG.
    • Experimental names and internal modules are outside this policy.

    Python versions¶

    requires-python is >=3.10, following Pinocchio's own support window. CI tests Python 3.10 (lowest), 3.12 (main) and 3.14 (highest).
